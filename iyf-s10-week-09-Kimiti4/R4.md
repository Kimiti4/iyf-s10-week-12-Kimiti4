# 0. CONSTITUTIONAL AUTHORITY

R4 is a **route/API integrity phase**.

Its purpose is to establish that the application's:

```text
Frontend route
    ↓
API client
    ↓
HTTP method/path
    ↓
Backend route
    ↓
Middleware
    ↓
Controller
    ↓
Service/repository
    ↓
Database
```

forms a coherent, reachable, correctly authorized, truthfully behaving contract.

R4 is not a feature-expansion phase.

Do not implement missing business capabilities merely because an endpoint or frontend route currently lacks one.

---

# 1. R4 SCOPE

R4 owns route/API integrity issues remaining after R1–R3.

Primary targets include:

* frontend/backend route mismatches;
* incorrect HTTP methods;
* incorrect API paths;
* dead or unreachable API registrations;
* frontend routes pointing at obsolete endpoints;
* backend endpoints with no valid consumers;
* authorization middleware inconsistencies;
* route-level IDOR/BOLA exposure discovered during route tracing;
* incorrect status-code contracts;
* malformed request/response contracts;
* duplicate/legacy route definitions;
* stale API client definitions;
* incorrect parameter placement;
* route registration omissions;
* route shadowing/order problems;
* route behavior inconsistent with R3's explicit `501` dispositions.

R4 may investigate related P2/P3 API findings where they are directly necessary to establish route integrity.

# 10. AUTHORIZATION INTEGRITY

R1/R2 established important security boundaries.

R4 must ensure route wiring does not accidentally bypass them.

For every authenticated route determine:

```text
anonymous
    → expected status

authenticated ordinary user
    → expected status

    → expected status

unauthorized authenticated user
    → expected status

moderator/admin
    → expected status
```

Specifically test for:

* IDOR;
* BOLA;
* missing ownership checks;
* role middleware omission;
* middleware attached to one route alias but not another;
* unprotected legacy routes;
* duplicate route definitions with weaker middleware.

### Critical rule

If two paths expose the same resource, both paths must have equivalent security guarantees.

A protected canonical route must not be undermined by an unprotected legacy alias.
