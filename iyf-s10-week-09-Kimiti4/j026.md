J-021 — JAMII LINK PROFESSIONAL UI/UX REVAMP
============================================================

ROLE
------------------------------------------------------------
You are the Senior Frontend Architect, Product Designer, and
UI/UX Engineering Lead for JamiiLink.

You are NOT performing a cosmetic CSS cleanup.

You are upgrading JamiiLink from a technically functional social
platform into a polished, distinctive, production-quality social
product.

The current application already contains substantial functionality:
- Posts
- Reels
- Unified feed
- Jams
- Notifications
- Discovery
- Creator Studio
- Mtaani
- Skills
- Farm
- Gigs

- Quests

- Authentication
- Responsive layouts
- Dark mode
- Mobile bottom navigation
- Sidebar navigation

DO NOT rewrite working functionality.

DO NOT create a new frontend architecture.

DO NOT replace React Router, existing providers, APIs, hooks,
domain logic, or working components unless there is a demonstrated
technical reason.

This is a PROFESSIONALIZATION AND DESIGN-SYSTEM MILESTONE.

============================================================
1. PRIMARY PRODUCT OBJECTIVE
============================================================

JamiiLink should feel like:

    X + TikTok + community infrastructure + creator platform

but it must NOT look like a clone of any of them.

The product should communicate:

    "This is a modern social network built around communities,
     people, creation, participation, and real-world activity."

The UI must have its own visual identity.

The user should immediately understand:

    Home
    Discover
    Reels
    Jams
    Communities
    Activity
    Create

without feeling overwhelmed by the number of features.

The product should feel:
- modern
- confident
- premium
- social
- energetic
- clean
- trustworthy
- approachable
- distinctly African/community-oriented without relying on clichés
- suitable for creators
- suitable for everyday users
- suitable for organizations
- suitable for professional/community use

============================================================
2. NON-NEGOTIABLE DESIGN PRINCIPLE
============================================================

Every page must look like it belongs to the SAME PRODUCT.

Do not independently style pages.

Establish a coherent visual system and apply it across:

    AppShell
    Sidebar
    Navbar
    MobileBottomNav
    Feed
    Posts
    Reels
    Jams

Do NOT scatter:
    #hexcolor
    rgb(...)
    arbitrary shadows
    arbitrary border-radius values
    arbitrary spacing
    arbitrary font sizes

through individual components.

============================================================
3. FIRST STEP — AUDIT BEFORE MODIFYING
============================================================

Before writing code:

Inspect the actual frontend.

Identify:

    package.json
    src/App.jsx
    src/index.css
    src/styles/*
    src/components/*
    src/pages/*

    Sidebar

    responsive CSS
    dark-mode implementation
    route structure

Determine:

1. Which styles are canonical.
2. Which styles are duplicated.
3. Which components already have good structure.
4. Which components are visually inconsistent.
5. Which routes are broken.
6. Which routes render but feel unfinished.
7. Which CSS rules conflict across breakpoints.
8. Whether desktop/tablet/mobile use different shells.
9. Whether dark mode is token-consistent.
10. Whether any current visual fix would break Lighthouse/CLS.

DO NOT blindly replace existing CSS.

Create a short internal audit before implementation.

============================================================
4. VISUAL DIRECTION
============================================================

Use a restrained modern design language.

Primary visual characteristics:

    soft neutral surfaces
    strong typography
    indigo/blue-violet brand identity
    restrained accent colors
    subtle borders
    subtle elevation
    large clean content surfaces
    generous spacing
    compact navigation
    strong active states
    minimal gradients
    controlled motion

Avoid:

    excessive gradients
    neon colors
    excessive rounded cards
    cartoonish UI
    huge shadows
    rainbow interfaces
    oversized icons
    excessive emoji
    excessive glassmorphism
    decorative elements that compete with content
    "dashboard template" appearance

JamiiLink should look like a serious consumer social platform.

============================================================
6. APP SHELL — HIGHEST PRIORITY
============================================================

The AppShell is the foundation of the experience.

Desktop:

    ┌─────────────────────────────────────────────────────────┐
    │                       NAVBAR                            │
    ├──────────────┬─────────────────────────┬───────────────┤
    │              │                         │               │

    main content max-width: 720–820px for feed-like screens

The sidebar should feel like product navigation,
not an HTML list.

============================================================

Current sidebar feels amateurish.

Rebuild the VISUAL EXPERIENCE while preserving route functionality.

Recommended structure:

    JAMII LINK
    ─────────────────

    HOME
    DISCOVER
    REELS
    JAMS

    COMMUNITY
    ─────────────────

    Notifications
    Messages

    ─────────────────

    Creator Studio
    Saved
    Drafts

    ─────────────────
    Settings
    Help / Feedback

The principle is:

    PRIMARY
    COMMUNITY
    ACTIVITY
    PERSONAL
    SYSTEM

The sidebar must visually communicate hierarchy.

------------------------------------------------------------
SIDEBAR VISUAL RULES
------------------------------------------------------------

Width:

Desktop:
    approximately 240–260px

Tablet:
    approximately 210–230px where persistent navigation remains

Mobile:
    do NOT squeeze the desktop sidebar into the viewport.

Use the existing mobile navigation model.

Sidebar items:

    height: 42–48px
    consistent icon width
    consistent left alignment
    controlled spacing

Icons:

    18–20px

Text:

    14–15px
    medium weight

Active item:

    subtle brand background
    brand-colored icon
    stronger text weight
    optional left indicator

Hover:

    subtle surface-hover
    no dramatic animation

Do NOT use huge gradients for active navigation.

Do NOT make every item look like a button.

Section labels:

    uppercase or small-caps
    tiny
    muted
    increased letter spacing

Logo:

    clean
    compact
    visually distinctive

User area:

    profile avatar
    name
    optional role/status
    compact account controls

The user area should look like a polished social application,
not a generic admin dashboard.

------------------------------------------------------------
SIDEBAR COLLAPSED STATE
------------------------------------------------------------

Desktop collapsed:

    icons remain
    labels disappear
    tooltips become available
    width approximately 68–76px

Maintain identical vertical rhythm.

Do NOT create separate styling systems for collapsed navigation.

Use the same semantic tokens.

------------------------------------------------------------
SIDEBAR MOBILE
------------------------------------------------------------

Mobile should use the established mobile navigation architecture.

Do not introduce a desktop sidebar width at mobile breakpoints.

The mobile navigation should prioritize:

    Home
    Discover
    Create
    Reels
    Jams

or the best five primary actions based on the actual product.

Use a centered elevated Create action if appropriate.

The bottom bar should look like a deliberate mobile product
navigation system.

============================================================
8. MOBILE BOTTOM NAVIGATION
============================================================

Redesign it as a premium mobile navigation surface.

Requirements:

    fixed bottom
    safe-area support
    subtle top border
    appropriate background
    5 primary destinations maximum
    active indicator
    icon + compact label
    accessible touch targets

Avoid:

    oversized icons
    excessive colors
    thick shadows
    too many menu items

Recommended concept:

    Home     Discover    +Create    Reels     Jams

The Create action may receive special visual emphasis.

Do not make the bar visually louder than the feed.

============================================================
9. NAVBAR
============================================================

Navbar must visually integrate with sidebar.

Desktop:

    logo
    search
    primary context/actions
    notifications
    profile/create

Avoid stuffing every feature into the navbar.

Mobile:

    logo
    compact search/action
    notification/avatar/menu

Search should look like a real social platform search field.

Buttons should follow the global button system.

============================================================
10. ALERTS PAGE — P0 REDESIGN
============================================================

Alerts must NOT look like ordinary notifications.

Alerts represent information requiring attention.

Create a professional information architecture.

Page header:

    Alerts
    Stay informed about important events in your community.

Then summary:

    Active
    Important
    Community
    Resolved

Use real data when available.

------------------------------------------------------------
ALERT SEVERITY SYSTEM
------------------------------------------------------------

Emergency:

    danger semantic token

Important:

    warning semantic token

Community:

    info/brand semantic token

Informational:

    success/neutral semantic token

Do NOT simply color the entire card.

Use small severity indicators.

------------------------------------------------------------
ALERT CARD
------------------------------------------------------------

Design:

    severity indicator
    title
    concise description
    timestamp
    location/community
    source
    status
    action

Example:

    ┌────────────────────────────────────────────┐
    │ ● EMERGENCY                    12 min ago │
    │                                            │
    │ Heavy rainfall warning                    │
    │                                            │

    │                                            │

    │                                            │
    │ [View details]                 [Acknowledge]│
    └────────────────────────────────────────────┘

Cards must be scannable.

Avoid giant alert cards.

------------------------------------------------------------
ALERT FILTERS
------------------------------------------------------------

Provide a compact filter system:

    All
    Emergency
    Important
    Community
    Informational

If there is enough data:

    Nearby
    Following
    Recent

Do not build decorative filters that don't change state.

------------------------------------------------------------
ALERT STATES
------------------------------------------------------------

Implement proper:

    Loading
    Empty
    Error
    Loaded
    Unread
    Read

Empty:

    clear explanation
    useful next action

Error:

    human-readable message
    Retry button

Loading:

    skeleton matching final card geometry

Do NOT use a generic spinner where a skeleton is more appropriate.

NOTIFICATIONS:

    "Someone liked your post."
    "You were mentioned."
    "Someone joined your Jam."

ALERTS:

    "Heavy rainfall warning."
    "Community safety notice."
    "Important local information."

Do not merge these concepts visually.

    Reel

Create reusable patterns:

    PageSkeleton

    EmptyState

Use:

    elevated surfaces
    subtle borders
    controlled brand accent
    readable secondary text

No bright saturated cards.

    Mobile ~768px
    Mobile ~390px
    Mobile ~360px

    compact navbar
    no horizontal overflow
    touch-friendly controls
    single-column content
    appropriate modal behavior

Respect the existing mobile architecture.

============================================================
24. MOTION
============================================================

Use subtle transitions:

    120–220ms

Examples:

    hover
    active
    menu opening
    modal
    toast
    feed insertion

Avoid:

    unnecessary page animations
    excessive bounce
    slow transitions
    animation on every element

Respect:

    prefers-reduced-motion

============================================================
25. ACCESSIBILITY
============================================================

Although J-022 is the formal accessibility milestone,
J-021 must not introduce accessibility regressions.

Minimum:

    semantic navigation
    button labels
    aria-label where needed
    visible focus
    keyboard navigation
    sufficient contrast
    meaningful heading hierarchy
    alt text
    accessible mobile nav
    accessible modal behavior

Never use:

    div pretending to be button
    clickable span without reason
    icon-only controls without accessible names

============================================================
26. CODE QUALITY RULES
============================================================

STRICT.

1. Reuse components before creating new ones.

2. Reuse design tokens before creating new values.

3. One responsibility per component.

4. No giant JSX components.

5. No 500-line CSS files created merely to style one page.

6. No duplicated utility functions.

7. No duplicated formatTime/date/number formatting logic.

8. No duplicated button/card styles.

9. No inline style unless the value is genuinely dynamic.

10. Avoid !important.

11. Avoid CSS specificity wars.

12. Do not create circular imports.

13. Do not introduce unused dependencies.

14. Do not introduce unused components.

15. Do not leave console.log/debug statements.

16. Do not suppress ESLint warnings.

17. React hooks must have correct dependency arrays.

18. Do not fix React effects by disabling lint rules.

19. Prefer stable references for hook dependencies.

20. Do not create objects/arrays inline when they become effect
    dependencies unless memoization is appropriate.

21. Avoid unnecessary re-renders.

22. Preserve React.memo where it actually helps.

23. Do not prematurely optimize everything.

24. Preserve AbortController behavior in async feed requests.

25. Preserve existing lazy loading.

26. Preserve Lighthouse-friendly layout stability.

27. Do not introduce image layout shifts.

28. Every image should have predictable dimensions/aspect ratio.

29. Do not load large libraries for trivial UI functionality.

30. Route-level functionality must remain lazy-loaded where
    appropriate.

31. Never hide broken functionality behind fake UI.

32. If an API is unavailable, use the application's established
    fallback architecture rather than introducing ad-hoc mocks.

33. Do not modify backend contracts unless explicitly required.

34. Do not rename APIs simply for aesthetics.

35. Do not remove working features.

36. Do not silently change business logic during a UI task.

37. CSS must be organized by responsibility.

38. Use semantic class names.

39. Avoid names such as:
       .box
       .thing
       .new-card
       .final-container

40. Prefer:
       .sidebar-section
       .alert-card
       .alert-severity
       .feed-header
       .creator-stat

### Recommended J-021 certification philosophy

The important change here is that **J-021 should become a quality gate, not another feature sprint**.

The agent should first tell you the uncomfortable truth about the current application:

> **What actually works? What merely renders? What is partially implemented? What is fake/fallback? What is broken? What is inaccessible? What is unreachable? What is inconsistent?**

Then it fixes the important failures and **re-certifies them**.

The final result should therefore look more like:

| Area          | Audited | Certified | Partial | Not Certified | Blocked |
| ------------- | ------: | --------: | ------: | ------------: | ------: |
| Pages         |      28 |        24 |       2 |             1 |       1 |
| Features      |      63 |        55 |       5 |             2 |       1 |
| Navigation    |      31 |        30 |       1 |             0 |       0 |
| Tier-1        |      10 |        10 |       0 |             0 |       0 |
| User Journeys |       8 |         8 |       0 |             0 |       0 |

The **numbers above are illustrative**, not a prediction of JamiiLink's actual state. The agent must derive the real numbers from evidence.

Most importantly, **do not allow a 90% overall score to hide a broken Jams, Alerts, authentication, or primary navigation path**. Tier-1 certification should act as a hard gate.

This gives J-021 a much stronger role in the project: **J-020 proved that the application can perform; J-021 proves that the application is coherent, complete, usable, and professionally shippable.**
