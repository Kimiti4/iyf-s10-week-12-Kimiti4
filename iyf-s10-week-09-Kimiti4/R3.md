## MOCK DATA RULE

Synthetic, hardcoded, fabricated, placeholder, seeded-demo, randomly generated, or otherwise non-authoritative data MUST NOT be presented to users as if it were real production capability.

For every discovered mock:

### Option A — REAL

Connect the feature to the authoritative backend/data source and prove it.

### Option B — UNAVAILABLE

Return an explicit, truthful unavailable state.

### Option C — TEST/DEMO ONLY

Isolate it so that it cannot be mistaken for production functionality.

### Forbidden

Do not:

* replace one hardcoded dataset with another;
* generate fake values dynamically and call them real;
* fabricate database records merely to satisfy tests;
* silently fall back from a failed real service to synthetic data;
* report successful execution when the underlying capability failed;
* label placeholder metrics as user statistics;
* preserve mock behavior merely because the UI expects data.

# 13E. NO IMPLICIT AUTHORIZATION

The following principle is mandatory:

> **A STOP report is evidence, not permission.**

The agent must never infer authorization from:

* previous phase authorization;
* successful tests;
* its own recommendation;
* completion of a STOP report;
* absence of objections;
* a general instruction to "continue";
* a previous Git authorization;
* completion of an earlier remediation phase.

Authorization is **phase-specific and scope-specific**.

R1 authorization does not authorize R2.

R2 authorization does not authorize R3.

R3 authorization does not authorize R4, R5, or R6.

A Git authorization does not authorize unrelated code changes.
